# FORMA-248 custody and rotation handoff

This directory is an operator recipe, not proof of a deployed environment. The former AWS environment was deliberately deleted. Billable reconstruction needs the coordinated test window, budget, named operator and GenUI callback origin. FORMA-247 source qualification precedes this work; its hosted acceptance and GenUI APP-058 acceptance remain separate gates.

## Contract

- Access tokens remain `alg=EdDSA`, `typ=JWT`; public keys remain `kty=OKP`, `crv=Ed25519`, `use=sig`, with unpadded base64url `x`. `kid` remains base64url of the first eight SHA-256 bytes of the public key. Issuer, audience and tenant claims follow FORMA-247's registered tenant/client contract.
- [AWS KMS keys](https://docs.aws.amazon.com/kms/latest/developerguide/symm-asymm-choose-key-spec.html) must be customer managed, enabled, `Origin=AWS_KMS`, `KeyUsage=SIGN_VERIFY`, `KeySpec=ECC_NIST_EDWARDS25519`. Signing uses `ED25519_SHA_512` with `MessageType=RAW`, never the prehash variant. Signing inputs over 4096 bytes fail before calling KMS. Every returned signature is checked against the loaded public key before emitting a token.
- The process receives immutable key ARNs and public keys, never signing private bytes. `FAUTH_REQUIRE_KMS=true` is mandatory for this environment. Malformed configuration, startup metadata failure, unknown algorithms, unavailable signing, a stale generation or invalid signatures fail closed. There is no PEM fallback in KMS mode. Explicit local mode is development/legacy only and never clears APP-058.
- JWKS includes current, next, unexpired previous access keys, and a separate immutable SSF public key. [SSF 1.0 §4.1.7](https://openid.net/specs/openid-sharedsignals-framework-1_0.html) forbids `exp`; its historical security events and retained outbox entries use that dedicated signer, `typ=secevent+jwt`, without expiry. The SSF key cannot verify access tokens and is not retired by access-key rotation. Changing the SSF key needs a separately reviewed historical-verification migration.
- The access lifetime cap is persisted in every manifest and cannot shrink. Runtime expiry may be smaller. Previous access keys stay available through the last possible issuance plus this cap plus 60 seconds. Refresh tokens are opaque database secrets, not signed JWTs; their 30-day lifetime does not extend the access-key overlap.

## Approved-window preparation

1. Finish FORMA-247 hosted tenant/client setup and confirm the exact HTTPS callback with GenUI. Keep credentials in the approved secret channel; never paste them into receipts.
2. Use a clean reviewed checkout and immutable image tag. The image builder checks tracked and nonignored untracked changes before any registry login, builds from an immutable Git archive, and builds the frontend inside a Node stage using the committed npm lockfile. Host `admin/dist` is excluded. Rust uses three build jobs by default. `build-identity.json` inside the runtime records the source revision, npm-lock digest, manifest digest and every emitted asset digest; `/health` reports the compiled revision. Use `scripts/build_local_image.sh <local-tag>` for an amd64 qualification without registry authentication or push. Record the ECR digest and observed health revision.
3. In the selected region/account, create three AWS-generated Ed25519 signing keys: access A, next B and independent SSF S. A trial promotion requires a fourth fresh key C. Use `aws kms create-key --key-spec ECC_NIST_EDWARDS25519 --key-usage SIGN_VERIFY --origin AWS_KMS` with environment/owner tags and descriptions; retain only public ARN/metadata receipts. Set key policy to permit the environment role's scoped IAM policy. Key administrators must be separate from the runtime role. Never import a private key or reuse the deleted file-key secret.
4. Copy `keyring.example.json`, replacing its synthetic ARNs, and pass the JSON object as `gatewasm:staging:kmsKeyring`. Remove/empty `Ed25519Key` and `SsfSigningKey` secret references. CDK rejects mixed custody configurations. Runtime IAM permits DescribeKey/GetPublicKey on the ring and Sign only on A and S, with [RAW/SHA512 conditions](https://docs.aws.amazon.com/kms/latest/developerguide/conditions-kms.html). Next/previous keys get no Sign permission.
5. Provision platform/admin and tenant management credentials in Secrets Manager. The service only reads the platform key; tenant database rows contain management-key hashes and prefixes. Provisioning/rotation operators have narrowly scoped write/version-stage permissions; the runtime has no Secrets Manager write/rotation or KMS administrative permissions. Keep provider credentials out of this synthetic email-only rehearsal unless actually needed.
6. Synthesize and review the exact selected staging network/data/service stacks, source image digest, policies and secret references. The normal CDK app also defines production and CDN stacks: never use `--all` for this rehearsal. See the coordinated reconstruction/cost plan for eligibility, expiry and teardown. No cloud mutation was executed by the local qualification.

## Versioned access-key promotion

One named operator owns deployment and rotation. Do not edit the version table manually. Each manifest change is a reviewed deployment, incrementing `version` by exactly one. Startup persists it under a PostgreSQL advisory transaction lock. Same-version identical restarts are allowed; stale versions and same-version content changes are refused. Version history is public operational state and must be retained through backup/restore.

1. **Publish:** deploy v1 with A current, B next, S dedicated SSF. Check the successful deployment operation, source revision, health and public JWKS. Confirm every serving replica uses this generation; merely inserting the manifest in the database is insufficient. No stopped/old replica may still accept traffic.
2. **Witness:** record a public receipt identifying that completed deployment and observed kids. Deploy v2 with the same key set and `publication={"next_key_id":"<B ARN>","all_replicas_serving_since":<UTC Unix seconds>,"evidence":"<durable receipt reference>"}`. The timestamp must be at/after v1 activation and not in the future. Preserve the exact witness in subsequent same-key versions. Wait at least 3600 seconds from this proven fleet publication, matching JWKS `Cache-Control: public,max-age=3600`.
3. **Promote:** create fresh next key C; deploy v3 with B current, C next, S unchanged, `publication:null`, and `previous:[{"key_id":"<A ARN>","last_issued_at":null,"retire_after":null,"drain_receipt":null}]`. The old key is initially retained indefinitely. IAM now permits Sign only on B and S. Stale replicas refuse signing, JWKS and health; transient 503 responses are possible during rollout. This design does not promise zero downtime.
4. **Drain:** wait for the completed deployment and prove every A signer is terminated/drained, including in-flight requests. Use a timestamp no earlier than the latest possible A issuance, not the first B startup. Persist the deployment/drain receipt. Deploy v4 setting A's `last_issued_at` to that timestamp, `retire_after >= last_issued_at + max_access_lifetime + 60`, and `drain_receipt` to the evidence reference. B's next refresh must succeed; tokens signed by A must still verify during overlap. Witness C publication independently before any future promotion.
5. **Retire:** at the boundary, serving instances omit A from JWKS and their access verifier; a cached consumer may retain A's public key up to its cache TTL, but all legitimate A access tokens have expired including skew. Record before/after JWKS and verification outcomes. Remove A's expired entry in a new manifest version; revoke its remaining public metadata IAM permissions and schedule its provider retirement according to the approved retention plan. Expired keys cannot be republished, arbitrarily re-added as previous, or reused as next. Keep public receipts and version history.

A database restore must retain the latest approved generation history. Do not start a restored older snapshot behind the same issuer while a newer environment can serve; isolate it, reconcile generation history, and requalify before traffic.

## Management-key rotation

`rotate-management.py` expects a secret containing `tenant_id` and `management_key`, as created by the FORMA-247 provisioner. It requires a fresh canonical UUID for a new operation and the same UUID on every retry:

```sh
python3 handoff/forma-248/rotate-management.py \
  --auth-origin https://CHOSEN_AUTH_HOST \
  --secret-id CHOSEN_TENANT_MANAGEMENT_SECRET_ARN \
  --region us-east-1 --operation-id CHOSEN_CANONICAL_UUID
```

Supply `FAUTH_PLATFORM_KEY` through the approved secret environment. No key appears in command arguments, stdout or receipts. The command writes an AWSPENDING version first, switches the tenant hash through the platform API, promotes that exact version to AWSCURRENT, then proves new-key HTTP 200 and revoked-key HTTP 401. It retains the prior secret version for recovery. A crash after staging or after the API switch can be resumed with the same UUID. An obsolete operation cannot intentionally overwrite a later observed current version. Unexpected redirects are rejected.

This is deliberately a single-operator protocol: the pending/obsolete checks are snapshots, not a distributed lock. Do not run two operators concurrently. The API and Secrets Manager switch is not atomic; consumers using the old secret can fail briefly until they reload AWSCURRENT. A different UUID must not be used to repair a partial operation. Every accepted management/platform request is durably audited before its handler runs, without key material or URL query strings; unavailable audit storage blocks the privileged action.

For the **platform key**, stage a fresh `plat_` value in its existing managed secret, record the nonsecret version ID, promote AWSCURRENT and redeploy every instance so App Runner reloads it. Prove the new value succeeds and the previous value is denied through every serving instance. Retain the prior version for recovery, never print either value, and only remove pending status after fleet convergence. A mixed rolling fleet can temporarily accept different platform values; stop privileged operations during this interval. This platform rotation is an operator runbook, not an automated cross-service transaction, and needs the staged live trial.

## Required live evidence and rollback

Capture sanitized source/image/KMS/secret version references and UTC timestamps, not JWTs, refresh tokens, private material or bearer keys. Required evidence:

- DescribeKey/GetPublicKey and a real issued token verified offline from public JWKS by kid; host configuration and IAM show no private signing-secret path. Verify KMS's origin and algorithm, not just the ARN naming convention.
- Refresh across A→B, prepublication witness, old-token overlap/expiry, before/after JWKS and stable SSF verification. GenUI independently tests its unknown-kid one-refetch-per-minute refusal contract and accepts APP-058.
- An unauthorized principal and the runtime's next/previous-key Sign attempts must be denied. Use fixed synthetic input; never mint a real user's token for a negative control. Capture AWS denial/event identifiers only.
- Temporarily deny the staged runtime's active-key Sign permission, prove login/refresh emits no token, restore the reviewed policy and prove recovery. A refresh transaction rolls back on signing failure so the same refresh can retry; an already consumed authorization code needs a new hosted login. Startup with inaccessible metadata must fail rather than create an ephemeral key. Retain CloudTrail operation receipts and audited management/platform use/rotation records.
- Local tests inject a remote signer and verify signature integrity, size/TTL bounds, failure/recovery, refresh rotation, single-use refresh behavior, stale generation handling, managed rotation interruption recovery and least-privilege synthesis. These do not prove an AWS policy denial, actual non-exportability, hosted availability or GenUI integration.

Rollback the application binary only if it supports the **current** manifest/schema and the same approved KMS contract. Old manifests are refused, and historical retired key ARNs cannot be promoted again. If the current signer is unusable, stop issuance, repair access to that key or advance through a fresh prepublished KMS key with the required window. Do not bypass publication/overlap/history guards to regain availability. Restoring a file-key implementation immediately reopens APP-058 and prohibits real-organization sign-in; it is not a custody-preserving rollback. Preserve database history and public evidence for requalification. SSF signing failure emits no unsigned event; the existing event emitter logs failure, so delivery completeness during an outage needs separate operational reconciliation.
