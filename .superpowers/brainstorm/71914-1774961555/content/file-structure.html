Why console-v2/ instead of modifying console/

  • Zero risk to live product. Current console keeps working. No merge conflicts, no broken states.
  • Clean separation. Wizard code, new views, new store — all in one place. No stitching into the old monolith.
  • Atomic swap. When Phase 3 is complete, update the build config to point /platform/console at console-v2/app.ts and delete the old folder.
  • Independent development. New entry point in build.ts during dev (/platform/console-v2), old one stays at /platform/console.

Build Config Change

// build.ts — during development, both exist
{ entry: 'src/platform/console/app.ts',    outfile: 'platform-console.js' },     // live
{ entry: 'src/platform/console-v2/app.ts', outfile: 'platform-console-v2.js' },  // dev

// After swap — v2 replaces original
{ entry: 'src/platform/console-v2/app.ts', outfile: 'platform-console.js' },

// Rust server — add dev route during development
.route("/platform/console-v2", get(platform_dashboard::dashboard_page_v2))

Server-Side Changes (Rust)

Phase 1:
  New route:  GET /t/{slug}/sandbox     → sandbox page (tenant-scoped, admin-gated)
  New API:    GET /t/{slug}/auth/introspect → returns decoded JWT + session for current user
  DB change:  tenants table + onboarding_completed (bool), preferred_tab (text nullable)
  Branding:   PATCH /platform/self-serve/tenants/{id} already supports name + primary_color

Phase 2:
  New route:  GET /platform/console-v2  → serves console-v2 page (dev only, swaps later)
  New APIs:   GET /manage/users (already exists), search/filter params (may need additions)

Phase 3:
  New API:    GET/PUT /manage/hosted-page → read/write hosted page JSON blob
  New route:  GET /t/{slug}/site → auth-gated hosted page (S3/CF or server-rendered)
  DB change:  tenant_hosted_pages table (tenant_id, content_json, updated_at)
