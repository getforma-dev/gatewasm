Phase 1 Architecture: Onboarding Wizard + Sandbox

Two approaches for where the wizard lives and how it communicates with the sandbox page

A

Wizard Inside Console (Recommended)

The wizard is a new view mode within the existing /platform/console app. When a tenant has zero auth events, the console renders the wizard instead of the normal tenant detail view. Once complete, the wizard flag is saved to the tenant config and the normal console tabs appear.


Pros

  • Single app shell — sidebar, auth, state all reused
  • No new routes or server handlers needed for the wizard itself
  • Wizard state persists in the tenant record (server-side), not localStorage
  • Polling for first auth event uses existing API infrastructure
  • Easy to swap: wizard view → console tabs, same mount point

Cons

  • Console store grows — wizard state added to existing store
  • Wizard steps need their own sub-views within the console app
B

Wizard as Separate Page

The wizard gets its own route /platform/onboarding/wizard with its own app shell, separate from the console. After tenant creation, the user is redirected there. On completion, they're redirected to /platform/console.


Pros

  • Complete isolation — wizard code doesn't touch console code
  • Can be designed as a focused, distraction-free experience
  • Separate bundle — doesn't increase console JS size

Cons

  • New route, new server handler, new entry point, new build config
  • Full page navigation between wizard → console (flash)
  • Auth state must be re-established on the console page
  • Wizard state needs its own persistence mechanism
  • More infrastructure for a flow the user sees exactly once

Sandbox Page (Same in Both Approaches)

The sandbox is always a new standalone page at /t/{slug}/sandbox — a new entry point in admin/src/tenant/sandbox/ with its own app.ts, store, and component. It's tenant-scoped (Plane 3), auth-gated, and admin-restricted. This is the same regardless of which wizard approach we pick.
